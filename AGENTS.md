# AGENTS.md — правила работы над проектом

> Этот файл читается автоматически. Он задаёт стандарт качества.
> Приоритет: **качество > скорость**. При сомнении выбирай более тщательный путь.

## 1. Рабочий цикл (обязателен, не сокращать)

1. **Разведка.** До первой строки кода: прочитать все релевантные файлы, конфиги,
   `package.json`/`pyproject.toml`/`go.mod` и т.п., посмотреть существующий стиль,
   найти аналогичные реализации в проекте. Не писать код, пока не понятна картина.
2. **План.** Дать план: шаги, список файлов (абсолютные пути), риски, открытые вопросы.
   Ждать подтверждения перед реализацией.
3. **Реализация.** Маленькими шагами. Полные файлы, без `TODO`, без заглушек,
   без «здесь потом допишем». Минимальный необходимый дифф.
4. **Проверка.** Реально запустить сборку / проверку типов / линтер / тесты
   и показать вывод. Не утверждать «работает», если не запускал.
5. **Отчёт.** Что сделано; что проверено и чем; что НЕ проверено и почему;
   какие остались риски; что предлагается дальше.

## 2. Definition of Done (для каждой задачи)

- [ ] Код компилируется / типы проходят без ошибок
- [ ] Линтер и форматтер не дают новых замечаний
- [ ] На новую логику есть тесты; существующие тесты зелёные
- [ ] Нет `TODO`, `FIXME`, заглушек, мёртвого и закомментированного кода
- [ ] Обработаны ошибки и краевые случаи (пустые данные, `null`, сеть, таймауты)
- [ ] Обновлена документация, если изменилось поведение / API / команды
- [ ] Нет секретов, ключей и паролей в коде и в логах
- [ ] Дифф перечитан глазами: нет случайных правок, нет лишних переименований
- [ ] Соблюдён существующий стиль: имена, структура папок, обработка ошибок, логирование

## 3. Технические правила

- Никаких новых зависимостей без явного согласия.
- Не менять файлы вне скоупа задачи. Не «улучшать» попутно чужой код молча.
- Не выдумывать API, поля, эндпоинты, имена функций: проверять по коду, типам или докам.
  Если не знаешь — сказать «не знаю» и пойти проверить.
- Использовать только те библиотеки и паттерны, что уже есть в проекте.
- Явно объявлять допущения и ограничения решения.
- Все пути в отчётах — абсолютные.

## 4. Коммуникация

- Честно сообщать о неопределённости и о непроверенных местах. Не выдавать догадку за факт.
- Не расширять скоуп задачи молча — сначала спросить.
- При неоднозначном требовании задать вопрос, а не выбирать за пользователя.
- Писать по-русски, код и идентификаторы — по-английски.

## 6. Бэкенд: правило вертикальных слайсов

Бэкенд-задачи берём крупнее, поэтому:

1. Одна задача = **один вертикальный слайс** (например: «форма → Lead → Битрикс24» или «админка: CRUD моделей»).
2. Перед реализацией — **спека в `docs/specs/<слайс>.md`**, не длиннее страницы: сущности, эндпоинты, валидация,
   поведение при ошибках, что считается готовым.
3. Реализация — **строго по спеке**; если спека оказалась неверной, сначала правится спека, потом код.
4. Готовность слайса подтверждается тестами API (Vitest) и ручным сценарием, а не словами «должно работать».
5. Спека — это кэш контекста: в следующих задачах читается она, а не вся история переписки.
