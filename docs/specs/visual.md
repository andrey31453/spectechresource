# Визуальная работа: два режима, протокол вариантов, готовые промты

**Статус:** действует с 20.11.2026. Связано: `AGENTS.md` §0 (изображения) и §7 (режимы),
`docs/specs/front.md` §6 (правила замеров), `docs/specs/home.md` §3.3.2 (блок «Каталог моделей»).

## 1. Зачем два режима

Большую часть времени проект ведёт модель **без входа изображений**: скриншот для неё —
не данные, а ловушка (см. `AGENTS.md` §0). При этом решения о вёрстке по своей природе
визуальные. Разрешается противоречие так:

- **основной режим** — вёрстка проверяется числами (`npm run audit:visual`) и кодом,
  а вкус остаётся за человеком: модель предлагает 2–4 текстовых направления, человек выбирает;
- **дизайнерский режим** — включается отдельной фразой, когда в работе модель со зрением:
  тогда скриншоты становятся источником приёмки, но разметку всё равно подтверждаем кодом.

Режимы не смешиваются: правила одного не действуют в другом.

## 2. Режим «основной» (без скриншотов)

**Кто:** `deepseek/deepseek-v4-pro-0813` и любая модель без image input.

**Правила**

1. Изображения не открывать: `.png/.jpg/.webp/.pdf` — стоп, ответ по `AGENTS.md` §0.
   Просьбу «посмотри, как выглядит» переводим в текст: числа, `outerHTML`, `getComputedStyle`.
2. Любое изменение вёрстки подтверждается аудитом: `npm run audit:visual` (см. §5).
   Отчёт без прогона аудита не принимается — «должно выглядеть нормально» не аргумент.
3. Вкус не выбираем в одиночку: сначала 2–4 направления словами (композиция, типографика,
   палитра, что акцентируем), затем реализация выбранного. Если направления не согласованы —
   вопрос человеку, а не «сделаю как считаю лучше».
4. Один блок — один шаг: правка → `build` → `audit:visual --scope=<селектор>` → отчёт.
5. В отчёте — только факты: числа, классы, значения `getComputedStyle`, список проверок
   и список того, что **не** проверено.

**Чек-лист перед отчётом**

- [ ] горизонтального переполнения нет на 375 / 768 / 1280 (`document.scrollWidth ≤ viewport`);
- [ ] контраст всех текстовых пар ≥ AA (4.5:1, крупный ≥ 3:1);
- [ ] кликабельные цели ≥ 24 px (WCAG 2.5.8), тач-цели ≥ 44 px — где это кнопка, а не ссылка в тексте;
- [ ] картинки не битые, `alt` осмысленный;
- [ ] ошибок консоли нет;
- [ ] состояния `hover`/`focus-visible` проверены через CDP (`Input.dispatchMouseEvent` →
      `getComputedStyle`), а не «по коду видно»;
- [ ] `prefers-reduced-motion` выключает движение, но не состояние;
- [ ] `npm run lint` / `typecheck` / `test` / `build` зелёные.

**Шаблон отчёта**

```
Что сделано: <блок, файлы, 1–3 пункта>
Проверено: audit:visual 375/768/1280 — переполнение 0, контраст AA, цели ≥24, фото 92/0 битых,
           консоль 0 ошибок; hover через CDP: <свойство: было → стало>.
Не проверено: <например, реальный Safari на iOS, шрифтовой рендер Windows>.
Риски: <1–2 пункта>.
Дальше: <что предлагаю>.
```

## 3. Режим «дизайнерский» (зрение разрешено)

**Как включается:** пользователь пишет фразу вида
`дизайнерский режим: скриншоты разрешены, модель <имя> видит изображения`.
Только после этого правила `AGENTS.md` §0 на текущую задачу не действуют.

**Правила**

1. Скриншот — источник приёмки, но не источник истины о разметке: если на скриншоте
   «съехало», причина всё равно ищется в коде и `getComputedStyle`.
2. Сравнивать можно только снимки с одинаковым вьюпортом и `deviceScaleFactor` (иначе
   разница в рендере выдаётся за дефект вёрстки).
3. Что смотреть на снимке, в этом порядке:
   - **ритм**: отступы кратны 4/8, вертикальные интервалы между блоками одинаковы;
   - **иерархия**: в каждом блоке один визуальный акцент, остальное — служебное;
   - **читаемость**: строки не длиннее ~75 символов, нет «сирот» из одного слова, переносы осмысленные;
   - **обрезка**: фото не режет машину по важной части, выравнивание кропа по предмету;
   - **плотность**: есть «воздух» у крупных заголовков и плотность у метаданных.
4. Ничего не «правим на глаз»: каждое замечание превращается в число и правку в коде
   (например: «hero выше на 40 px», «радиус карточки 10 вместо 6», «кегль 15 → 16»).
5. Скриншоты не коммитим в репозиторий: они живут в переписке и в `data/tmp`.

**Как приложить снимок:** PNG в чат + подпись `вьюпорт 1280×900, состояние: hover на карточке 2`.

## 4. Протокол вариантов (сравнение «глазами»)

Когда не ясно, какой дизайн лучше, варианты не обсуждаются словами — они **рисуются рядом**:

1. **Данные общие.** Все версии получают одинаковые пропсы (модели, город, дисклеймер):
   сравнивается дизайн, а не контент.
2. **2–4 версии.** Каждая — свой компонент. На странице друг под друга, с подписью
   «Вариант A · Название» и одной строкой «на что смотреть».
3. **Якоря и навигация.** `#modeli-variant-a` … `#modeli-variant-d`, ссылки-таблетки сверху,
   чтобы прыгать между версиями без прокрутки 60 000 px.
4. **Идентификаторы не конфликтуют.** Внутренние `id` версий префиксованы (`modeli-a-…`),
   фокус и ленты у каждого варианта свои.
5. **Решение принимает человек.** Модель не удаляет варианты «за ненужностью».
6. **Закрытие.** Победившая версия остаётся, остальные удаляются вместе с подписями,
   навигацией и списком `HOME_MODEL_VARIANTS`; журнал правок — в `docs/specs/front.md`.

Текущий пример: блок «Каталог моделей» главной — `HomeModelsBlueprint` (A),
`HomeModelsShowroom` (B), `HomeModelsPassport` (C), `HomeModelsShowcase` (D),
подписи — `HomeModelsCaption`, список версий — `app/utils/model-variants.ts`.

## 5. Инструмент: `npm run audit:visual`

Headless Chrome по CDP, без скриншотов. Печатает отчёт по каждой ширине.

```bash
# сервер уже запущен (build + preview или dev)
npm run audit:visual -- --url=http://127.0.0.1:3001/
npm run audit:visual -- --url=http://127.0.0.1:3001/ --scope='#modeli'
npm run audit:visual -- --widths=375,768,1280 --json > /tmp/audit.json
npm run audit:visual -- --strict        # код 1 при переполнении, битых фото, ошибках консоли
```

| Флаг | Значение |
|---|---|
| `--url` | адрес страницы (по умолчанию `http://127.0.0.1:3000/`) |
| `--widths` | ширины вьюпорта через запятую (по умолчанию `375,768,1280`) |
| `--height` | высота вьюпорта (по умолчанию `900`) |
| `--scope` | селектор области проверки (по умолчанию `body`) |
| `--port` | порт DevTools (по умолчанию `9333`) |
| `--json` | сырой JSON вместо отчёта |
| `--strict` | код возврата 1 при дефектах |

Что печатает: размер документа против вьюпорта, элементы за правым краем (с пометкой
«внутри ленты» — это норма), битые фото, кликабельные цели меньше 24 px и компактные
24–43 px, пары текст/фон ниже AA (градиенты и фото исключаются — фактический фон неизвестен),
количество уникальных кеглей, число `h1–h3`, ошибки консоли.

Chrome берётся из `CHROME_PATH`, по умолчанию —
`/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`. Node — 24 (`nvm use`),
иначе ESLint падает на `Object.groupBy`: скрипты проекта запускать только после `nvm use`.

## 6. Готовые промты

### 6.1 Основной режим (модель без зрения)

```
Ты — ведущий фронтенд-инженер проекта spectechresource (Nuxt 4 + Tailwind 4).
Сначала AGENTS.md и docs/specs/visual.md §2, затем docs/specs/front.md.

Режим: ОСНОВНОЙ, изображений ты не видишь. Скриншоты не открывать — ни файл, ни base64.
Если пользователь приложил картинку: одна фраза «изображения не читаю» и сразу текстовый
эквивалент — абсолютные пути компонентов, `curl | grep`, числа замеров.

Задача: <что нужно сделать>.

Порядок работы:
1) Разведка: прочитай компоненты блока, его данные, стили и тесты. Покажи, что понял.
2) План: 2–3 ВАРИАНТА НАПРАВЛЕНИЯ СЛОВАМИ (композиция, типографика, цвет, акцент),
   список файлов, риски. Ждать выбора человека — код до выбора не писать.
3) Реализация выбранного: полные файлы, без TODO и заглушек.
4) Проверка: `npm run build`, `npm run audit:visual -- --scope=<селектор>`,
   состояния hover/focus через CDP. Показать фактический вывод.
5) Отчёт по шаблону из docs/specs/visual.md §2: что сделано / чем проверено /
   что НЕ проверено / риски.

Запрещено: «выглядит хорошо» без чисел; выдумывать CSS-переменные и токены; менять
блоки вне задачи; новые зависимости без согласия.
```

### 6.2 Дизайнерский режим (модель со зрением)

```
ДИЗАЙНЕРСКИЙ РЕЖИМ: скриншоты разрешены, модель видит изображения
(пользователь подтвердил это явно). AGENTS.md §0 на эту задачу не действует.

Ты — арт-директор и фронтенд-инженер проекта spectechresource (Nuxt 4 + Tailwind 4,
фирменные цвета: песочный #f5f4ef, графит #0d1214, оранжевый #ff7a2f / #cf4418 / #b83c12).
Сначала docs/specs/visual.md §3 и docs/specs/front.md.

Задача: <что нужно сделать>.

Порядок работы:
1) Разведка: код блока, данные, стили, замеры через CDP (`npm run audit:visual`).
2) Три направления словами + ссылки-референсы (URL), по 3 строки на каждое:
   композиция, типографика, цвет/акцент, что копируем и что НЕ копируем.
3) Ждать выбор. Реализовать выбранное; каждое замечание со скриншота переводить
   в число и правку в коде.
4) Проверка: скриншоты 375/768/1280 (+ hover и focus), аудит, контраст AA,
   переполнение 0. Показать и снимки, и числа.
5) Отчёт: что изменилось, что подтверждено снимком, что — замером.

Правило: снимок — приёмка, код — истина. Если расходятся — ищи причину в CSS,
а не «подгоняй» числа под картинку.
```

### 6.3 Промт-задача «варианты блока»

```
Задача: сделать несколько версий блока <селектор/название> и поставить их на страницу
друг под другом, чтобы человек сравнил глазами.

Требования:
- по одной версии на каждое направление: <список направлений>, плюс одна собственная
  версия «продающая, понятная, но дизайнерски интересная»;
- данные одни и те же; никаких заглушек вместо реальных моделей/цен;
- подписи «Вариант A · Название» + одна строка «на что смотреть»; навигация-якоря сверху;
- у каждой версии свои ленты/состояния: refs и state не должны пересекаться;
- новые scoped-классы с префиксом версии (`mva-`, `mvb-`, …), глобальных классов не добавлять;
- проверка: `npm run audit:visual -- --scope=<общий контейнер>` на 375/768/1280 —
  переполнение 0, контраст AA, цели ≥ 24 px, фото не битые, консоль чистая;
- в отчёте — таблица: версия / идея / что занимает / чем проверена. Выбор делает человек.
```
