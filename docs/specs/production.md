- GitHub Actions `Deploy production` запускается автоматически при push в `main`; также доступен ручной запуск.
  Secrets: `SSH_KEY` пока содержит SSH-пароль (историческое имя).
- Сборка и lint/test/typecheck выполняются в CI на Node 24. На сервере Node 24,
  PostgreSQL из Debian, systemd `spectech`, nginx, certbot с автопродлением TLS.
- `/opt/spectech/releases/<sha>-<run>` — релизы; `current` — текущий;
  `shared/app.env` (root, 600) — сгенерированные пароль БД и ключ сессий;
  `shared/uploads` — постоянные загрузки, `backups` — pg_dump перед миграциями.
- PostgreSQL не публикуется наружу; приложение слушает 127.0.0.1:3000.
- Перед `prisma migrate deploy` создаётся `pg_dump`. Применяются только ещё не применённые миграции из Git.
  Seed, импорт локальной БД и инициализация администратора из deploy удалены.
- Production-БД является источником рабочих данных: заявки, услуги, каталог, настройки и администраторы
  не заменяются обычной выкладкой.
- CRM отключена: NUXT_LEADS_DRY_RUN=true, webhook пуст. Заявки остаются в БД.
- После запуска — API health-check и HTTPS-проверки. При неудаче старта возвращается
  предыдущий symlink приложения. Миграции автоматически не откатываются: перед ними
  сохраняется dump; несовместимые миграции требуют отдельного плана.
- Ручной откат приложения: сменить `current` на прежний каталог и выполнить
  `systemctl restart spectech`. Перед восстановлением БД остановить приложение.
- Дальше: SSH-ключ/отдельный deploy-user вместо root-пароля, смена начального
  admin-пароля, внешние резервные копии и их ротация, перенос согласованного контента,
  мониторинг. Не запускать db:reset/db:migrate dev на production.

## Правила работающего production

- Push в `main` пересобирает приложение и выкладывает новый релиз. Миграции схемы выполняются безопасной командой
  `prisma migrate deploy`, без `db:reset`, `migrate dev`, `db push` и seed.
- Любое изменение данных (в том числе перенос обновлённых услуг и связей) — отдельная ручная операция с точным
  подтверждением, предварительным дампом и проверкой результата. Обычный deploy не разрешает замену production-БД.
- Для текущего переноса разрешён только согласованный набор: записи `services` и связи `_EquipmentTypeToService`,
  без заявок, админов, настроек, каталога техники и других таблиц. Услуги и виды сопоставляются по slug,
  production-ID сохраняются; отсутствующий вид останавливает транзакцию. Услуги вне переданного списка не удаляются.
- Отдельная команда: экспорт `node --env-file=.env --import tsx deploy/sync-services.ts export` в JSON,
  затем ручной workflow `Sync production services` с JSON в `payload` и точной фразой `SYNC SERVICES ONLY`.
  Перед импортом создаётся дамп; импорт меняет только поля переданных услуг и их связи с видами в одной транзакции.
  Изображения `/uploads/` отклоняются: файлы требуют отдельно согласованного переноса.
- Ошибка импорта откатывает всю транзакцию. Для отмены успешного импорта восстановить дамп в отдельную БД,
  экспортировать оттуда прежние услуги и перенести только их после отдельного подтверждения. Не восстанавливать
  полный дамп поверх работающей БД: это уничтожит новые заявки. Отдельно проверить новые услуги, которых не было в дампе.
