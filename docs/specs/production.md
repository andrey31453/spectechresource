# Первая production-выкладка

- Сервер: Debian 13, `root@129.101.113.247`; домен `specteh.online`.
- Ручной запуск GitHub Actions `Deploy production`, ветка `main`.
- Secrets: `SSH_KEY` пока содержит SSH-пароль (историческое имя),
  `ADMIN_PASSWORD_HASH` — scrypt-хеш пароля первого администратора.
- Сборка и lint/test/typecheck выполняются в CI на Node 24. На сервере Node 24,
  PostgreSQL из Debian, systemd `spectech`, nginx, certbot с автопродлением TLS.
- `/opt/spectech/releases/<sha>-<run>` — релизы; `current` — текущий;
  `shared/app.env` (root, 600) — сгенерированные пароль БД и ключ сессий;
  `shared/uploads` — постоянные загрузки, `backups` — pg_dump перед миграциями.
- PostgreSQL не публикуется наружу; приложение слушает 127.0.0.1:3000.
- Prisma migrate deploy; seed и текст земляных работ только при пустом каталоге.
  Локальная БД и загрузки автоматически не копируются; первый запуск — демо-контент.
- Существующая учётная запись администратора не перезаписывается.
- CRM отключена: NUXT_LEADS_DRY_RUN=true, webhook пуст. Заявки остаются в БД.
- После запуска — API health-check и HTTPS-проверки. При неудаче старта возвращается
  предыдущий symlink приложения. Миграции автоматически не откатываются: перед ними
  сохраняется dump; несовместимые миграции требуют отдельного плана.
- Ручной откат приложения: сменить `current` на прежний каталог и выполнить
  `systemctl restart spectech`. Перед восстановлением БД остановить приложение.
- Дальше: SSH-ключ/отдельный deploy-user вместо root-пароля, смена начального
  admin-пароля, внешние резервные копии и их ротация, перенос согласованного контента,
  мониторинг. Не запускать db:reset/db:migrate dev на production.
